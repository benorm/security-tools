# Socket Port Scanner

> 순수 `socket`으로 TCP Connect 스캔을 구현한 포트 스캐너.
> SYN 스캔(Scapy) 버전의 thread-safety 한계를 극복하고,
> 배너 그래빙으로 서비스 버전까지 탐지한다.

[English](./README.en.md) | 한국어

---

## 개요

이 프로젝트는 [syn-scanner](../syn-scanner)에서 마주친 한계를 해결하기 위해
출발했다. Scapy 기반 SYN 스캐너는 멀티스레딩 환경에서 thread-safety 문제로
작업자 수를 높이면 불안정했다. 이를 커널의 정상 `connect()`를 사용하는
순수 `socket` 구현으로 다시 작성하여, 안정성과 속도를 크게 개선했다.

나아가 연결된 서비스가 보내는 배너를 읽어, 열린 포트뿐 아니라
**서비스 버전 정보**까지 수집한다.

---

## SYN 스캔 vs Connect 스캔

두 방식은 커널 사용 여부에서 근본적으로 갈린다.

| | SYN 스캔 (syn-scanner) | Connect 스캔 (이 프로젝트) |
|---|---|---|
| 구현 | Scapy, raw socket | 순수 socket |
| 커널 | 우회 (직접 패킷 조립) | 사용 (정상 connect) |
| 핸드셰이크 | 미완성 (SYN→SYN/ACK→RST) | 완성 (SYN→SYN/ACK→ACK) |
| 권한 | root(sudo) 필요 | 일반 사용자 |
| thread-safe | ❌ 아니오 | ✅ 예 |
| 은밀함 | 높음 (로그 덜 남음) | 낮음 (연결 완성됨) |

핵심은 **은밀함과 안정성의 트레이드오프**다. SYN 스캔은 은밀하지만
thread-safe하지 않고, Connect 스캔은 은밀함을 포기하는 대신 안정성과
속도를 얻는다.

---

## 주요 기능

- **TCP Connect 스캔**: 커널 connect()로 안정적인 포트 탐지
- **thread-safe 멀티스레딩**: 스레드마다 독립 소켓 → 작업자 수백~수천 개도 안정적
- **배너 그래빙**: 열린 포트의 서비스 배너를 읽어 버전 정보 수집
- **유연한 포트 지정**: 범위(`1-1000`), 목록(`22,80,443`), 혼합 지원
- **서비스 식별**: 잘 알려진 포트에 서비스 이름 표시

## 설치 및 사용법

### 요구 사항

- Python 3.7+ (표준 라이브러리만 사용, 외부 의존성 없음)
- **root 권한 불필요**

### 사용 예

```bash
# 기본 스캔 (1-1000 포트)
python3 socket_scanner.py -t 192.168.0.10

# 포트 범위 지정
python3 socket_scanner.py -t 192.168.0.10 -p 1-10000

# 특정 포트만
python3 socket_scanner.py -t 192.168.0.10 -p 22,80,443,3306,8080

# 작업자 수 조절 (높여도 안정적)
python3 socket_scanner.py -t 192.168.0.10 -p 1-10000 -w 500

# 도움말
python3 socket_scanner.py --help
```

### 옵션

| 옵션 | 설명 | 기본값 |
|------|------|--------|
| `-t`, `--target` | 스캔 대상 IP (필수) | — |
| `-p`, `--ports` | 포트 범위/목록 | `1-1000` |
| `-w`, `--workers` | 동시 작업자 수 | `100` |

## 동작 원리

### Connect 스캔

`connect()`가 성공하면 포트가 열린 것이다. 커널이 3-way 핸드셰이크를
완성하므로, 반환값만 확인하면 된다.

```
connect_ex() == 0  → OPEN
connect_ex() != 0  → CLOSED
```

SYN 스캔과 달리 응답 패킷의 플래그를 직접 분석할 필요가 없다.
커널이 연결 성립 여부를 결과값으로 요약해 주기 때문이다.

### 배너 그래빙

일부 서비스는 연결되면 먼저 인사(배너)를 보낸다. 이를 읽으면
서비스 종류와 버전을 알 수 있다.

```
MySQL 연결 → "8.0.46 ... caching_sha2_password" 수신
→ 포트가 열렸을 뿐 아니라, MySQL 8.0.46이 돌고 있음을 파악
```

HTTP처럼 클라이언트 요청을 먼저 기다리는 서비스는 배너를 보내지 않으므로,
배너 수신은 실패해도 열림 판정에는 영향을 주지 않도록 처리했다.

## 성능 비교 (SYN 스캔 대비)

10,000개 포트를 스캔한 실측 결과다. 두 스캔 방식 자체의 성능을 비교하기 위해,
**배너 그래빙은 제외하고 측정**했다. (수치는 환경에 따라 달라질 수 있다.)

| 항목 | SYN 스캔 (Scapy) | Connect 스캔 (socket) |
|------|-----------------|----------------------|
| 작업자 40+ | 크래시 (thread-unsafe) | 안정 |
| 작업자 1000 | 크래시 | **안정** |
| 작업자 15, 소요 시간 | 약 26초 | 약 0.4초 |
| 속도 차이 | 기준 | 약 **65배 빠름** |

### 왜 이런 차이가 나는가

두 가지 요인이 곱해진 결과다.

1. **thread-safe**: socket은 스레드마다 독립적인 소켓을 생성하므로
   자원 충돌이 없다. Scapy는 내부 sniffer를 공유하여 작업자 수를 높이면
   경쟁 상태로 크래시했다. 그래서 socket은 작업자 수를 크게 높일 수 있다.

2. **개별 속도**: socket은 패킷 조립·응답 매칭 등 무거운 작업을
   커널(C로 구현된 고속 코드)에 위임한다. Scapy는 이를 파이썬 레벨에서
   처리해 느리다. 그래서 같은 작업자 수(15)로도 socket이 훨씬 빠르다.

## 한계 및 향후 개선

- **은밀함 없음**: 연결을 완성하므로 대상 로그에 남는다 (Connect 스캔의 본질)
- **배너 파싱 미흡**: 바이너리가 섞인 배너에서 버전만 정확히 추출하려면
  프로토콜별 파싱이 필요 → 현재는 출력 가능한 문자만 필터링
- **배너 그래빙의 대기 비용**: 배너를 보내지 않는 서비스(HTTP 등)에서는
  타임아웃만큼 대기가 발생해 스캔 시간이 늘어난다. 서비스 버전 정보를 얻기 위한
  트레이드오프이며, connect와 recv의 타임아웃을 분리하면 개선할 수 있다
- **결과 저장 없음**: 화면 출력만 지원 → JSON/CSV 내보내기 추가 예정
