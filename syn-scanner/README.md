# SYN Port Scanner

> Scapy로 TCP SYN 스캔을 직접 구현하며 nmap의 동작 원리를 이해하고,
> 멀티스레딩 적용 과정에서 마주친 기술적 한계를 분석한 프로젝트.

[English](./README.en.md) | 한국어

---

## 개요

`nmap`이 포트를 "열림/닫힘"으로 판별하는 그 과정을, 기성 도구에 의존하지 않고
**패킷 레벨에서 직접 재현**한 포트 스캐너입니다. Scapy로 SYN 패킷을 조립·전송하고,
응답의 TCP 플래그를 해석해 포트 상태를 판별합니다.

단순히 "동작하는 스캐너"를 넘어, 멀티스레딩을 적용하며 마주친
**파일 디스크립터 한계**와 **Scapy의 thread-safety 문제**를 직접 분석한 점에
초점을 두었습니다.

---

## 주요 기능

- **SYN 스캔**: 3-way 핸드셰이크를 완성하지 않는 half-open 방식
- **멀티스레딩**: `ThreadPoolExecutor`로 다수 포트 동시 스캔
- **유연한 포트 지정**: 범위(`1-1000`), 목록(`22,80,443`), 혼합(`1-100,8080`) 지원
- **서비스 식별**: 잘 알려진 포트에 서비스 이름 표시 (80 → HTTP 등)
- **결과 요약**: 열린 포트만 표시, 닫힌 포트는 개수로 요약

## 설치 및 사용법

### 요구 사항

- Python 3.7+
- Scapy (`pip install scapy` 또는 `sudo apt install python3-scapy`)
- raw socket 사용을 위한 **root 권한**

### 사용 예

```bash
# 기본 스캔 (1-1000 포트)
sudo python3 scanner.py -t 192.168.0.10

# 포트 범위 지정
sudo python3 scanner.py -t 192.168.0.10 -p 1-10000

# 특정 포트만
sudo python3 scanner.py -t 192.168.0.10 -p 22,80,443,3306,8080

# 작업자 수 조절
sudo python3 scanner.py -t 192.168.0.10 -p 1-10000 -w 15

# 도움말
python3 scanner.py --help
```

### 옵션

| 옵션 | 설명 | 기본값 |
|------|------|--------|
| `-t`, `--target` | 스캔 대상 IP (필수) | — |
| `-p`, `--ports` | 포트 범위/목록 | `1-1000` |
| `-w`, `--workers` | 동시 작업자 수 | `15` |

## 동작 원리

SYN 스캔은 TCP 연결을 완성하지 않고 포트 상태만 확인하는 기법입니다.

```
스캐너 → SYN → 대상
스캐너 ← SYN/ACK ← 대상   (열림: 서비스가 응답)
스캐너 ← RST/ACK ← 대상   (닫힘: 즉시 거부)
스캐너 ← (무응답)          (필터링 추정)
```

응답의 TCP 플래그로 상태를 판별합니다.

- `SYN/ACK` → **OPEN**
- `RST/ACK` → **CLOSED**
- 무응답 → **FILTERED**

일반적인 `connect()` 스캔과 달리 핸드셰이크의 마지막 ACK를 보내지 않아,
연결이 완성되지 않으므로 애플리케이션 레벨 로그에 덜 남습니다.

## 배운 점 · 마주친 한계

이 프로젝트에서 가장 많은 시간을 쏟은 부분은 "동작"이 아니라 "왜 그렇게 동작하는가"였습니다.

### 1. raw socket과 커널의 상호작용

Scapy는 커널의 TCP/IP 스택을 우회해 패킷을 직접 조립합니다. 이 때문에
커널은 스캐너가 보낸 SYN을 자신의 연결 테이블에 기록하지 않으며,
대상의 SYN/ACK 응답을 "모르는 연결"로 간주해 자동으로 RST를 보냅니다.
역설적으로 이 자동 RST가 SYN 스캔의 "연결 미완성"을 만들어 줍니다.

### 2. 멀티스레딩의 속도–안정성 트레이드오프

순차 스캔(1개 작업자)은 각 포트의 응답을 기다리는 시간이 누적되어 느립니다.
멀티스레딩으로 이 대기 시간을 병렬화하면 크게 빨라지지만, 작업자 수를
무작정 늘리면 오히려 문제가 생깁니다.

- 작업자 수를 1000으로 높이자 `select()`의 파일 디스크립터 한계(1024)를
  초과해 `filedescriptor out of range` 오류로 프로그램이 중단됨
- 즉, 동시성은 속도를 높이지만 시스템 자원 한계와 맞물려 있음

### 3. Scapy의 thread-safety 한계 (핵심)

작업자 수를 높이면(경험상 20 안팎부터 간헐적으로)
`OSError: [Errno 9] Bad file descriptor` 오류가 발생했습니다. 분석 결과,
이는 파일 디스크립터 개수 문제가 아니라 **Scapy가 thread-safe하지 않기
때문**이었습니다. 여러 스레드가 Scapy 내부의 소켓/sniffer를 동시에 정리하는
과정에서 경쟁 상태(race condition)가 발생한 것입니다.

이 한계를 인지하고, 안정적으로 동작하는 작업자 수(기본값 15)를 설정했습니다.
근본적인 해결은 Scapy 대신 저수준 소켓을 직접 사용하는 방향이며, 이는 향후
개선 과제로 남겨 두었습니다.

---

## 한계 및 향후 개선

- **Scapy thread-safety**: 높은 동시성에서 불안정 → 순수 `socket` 기반 재구현 검토
- **재전송 없음**: 응답을 놓치면 FILTERED로 오판 → retry 로직 추가 예정
- **결과 저장 없음**: 화면 출력만 지원 → JSON/CSV 내보내기 추가 예정
- **서비스 버전 미확인**: 포트 열림 여부만 판별 → 배너 그래빙 추가 검토
